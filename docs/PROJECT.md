# iOrder V2 — Tài liệu hệ thống

Tài liệu duy nhất mô tả kiến trúc, dữ liệu, bảo mật và vận hành. Hiện trạng, so sánh với CMS hiện đại và backlog nằm ở [ROADMAP.md](ROADMAP.md). Quy tắc cho agent nằm ở [AGENTS.md](../AGENTS.md).

## 1. Tổng quan

Website doanh nghiệp iOrder gồm site public và CMS quản trị nội dung. Đây là monorepo pnpm, Next.js 16 App Router, React 19, TypeScript, Tailwind CSS 4, Zod 4, PostgreSQL + Drizzle ORM, lưu media trên S3-compatible storage.

| App | Cổng local | Vai trò |
|---|---|---|
| `apps/website` | 3000 | Website public, render phía server, đọc dữ liệu qua Backend |
| `apps/admin` | 3001 | Giao diện CMS `/admin`, gọi Backend qua rewrite `/api`, `/media` |
| `apps/api` | 3002 | Route handlers `/api/*`, `/media/*`; app duy nhất truy cập DB và S3 |
| `packages/shared` | — | Drizzle schema, contracts (Zod), services, repositories dùng chung |

V1 (`D:\work\iorderwebsite\iorder-website`) chỉ là tài liệu tham khảo hành vi/dữ liệu; không copy kiến trúc hay source V1.

```text
apps/{api,admin,website}/   ba app Next.js độc lập
packages/shared/src/db/             Drizzle client + schema theo domain
packages/shared/src/server/<domain> contract → service → repository
drizzle/                          migration SQL + snapshot
scripts/                          seed, import V1, fixture audit, job dọn dẹp
compose.yaml                      PostgreSQL + S3Mock cho local
compose.production.yaml           stack production
Dockerfile, Caddyfile             build standalone đa stage, TLS/reverse proxy
```

### Luồng dữ liệu

```text
Browser → Caddy → admin | website ──rewrite/fetch──→ api → service → repository → PostgreSQL
                                                          └──→ S3 (SeaweedFS)
```

- CMS và website không có credential DB/S3; chỉ Backend có.
- website chỉ proxy `/api/v1/leads` và `/media/*` cho trình duyệt; dữ liệu render đọc thẳng `BACKEND_URL` từ server. API admin chỉ đi qua domain CMS.
- Mutation admin gọi `revalidatePath` (wrapper ở `apps/api/src/lib/publish-cache-revalidation.ts`). Wrapper gom lại và gửi **một** POST HMAC tới `website/api/internal/revalidate`, làm mới tag `public-content`. Data Cache public có TTL 60 giây làm dự phòng.

## 2. Mô hình dữ liệu

Mô tả đầy đủ từng bảng, cột, enum, JSONB và ảnh chụp dữ liệu local: [DATABASE.md](DATABASE.md).

Quy ước:

- UUID do database sinh, mọi bảng có `created_at`/`updated_at`.
- Vòng đời nội dung: `draft → review → scheduled → published → archived`. Xóa mềm bằng `deleted_at`. Nội dung hẹn giờ tự hiện khi `published_at <= now()`, lọc ngay lúc truy vấn, không cần job.
- Revision là snapshot JSONB bất biến, không thay cho `audit_logs`. `audit_logs` chỉ ghi thêm.
- Optimistic concurrency: mutation gửi `expectedVersion`; sai version trả HTTP 409, form giữ nguyên dữ liệu. Nội dung xuất bản dùng `draft_version`; cấu hình và danh mục (`site_settings`, `site_profile`, `redirects`, `categories`, `tags`, `partners`, `testimonials`, `equipment_groups`, `menus`) dùng cột `version`, API admin nhận `{ values, expectedVersion }` (bắt buộc khi sửa). Seed/script gọi service không truyền version thì bỏ qua kiểm tra.
- Media lưu `storage_key`, không lưu URL cố định; DTO dựng URL theo môi trường.
- Nơi lưu nội dung CMS: Trang chủ/trang tĩnh/trang tự tạo có metadata ở `pages`, mỗi khối ở `page_blocks` (`data` JSONB chứa các mục con; `appearance` chứa giao diện; thứ tự/trạng thái ở `sort_order/is_enabled`). Catalog lưu khối ở `offerings.content.blocks`, thiết bị ở `sales_equipment.blocks`, bài viết/hướng dẫn ở `posts.content`. Lịch sử nằm trong các bảng `*_revisions.snapshot`. Ảnh/tệp gốc ở S3, thông tin tệp ở `media_assets`; upload ghi thư viện ngay, gắn ảnh vào trang khi lưu nội dung. Bản đang nhập được giữ trong bộ nhớ của document CMS; mở preview tạo bản tạm ở `builder_previews` với TTL, không thay nội dung/revision. Compose local dùng volume `iorder-v2-postgres-data` và `iorder-v2-s3-data`; production dùng `postgres-data` và `seaweed-data`.
- JSONB chỉ dùng cho cấu trúc biến thiên (block, nội dung bài, section offering, thông số thiết bị) và luôn có Zod schema.
- Giá thiết bị là `bigint price_vnd`.

|---|---|
| Tài khoản & quyền | `users`, `roles` (`is_system` cho Super Admin), `permissions`, `user_roles`, `role_permissions`, `sessions`, `login_throttle_buckets` |
| Media | `media_assets` |
| Bài viết | `posts`, `post_revisions`, `categories`, `tags`, `post_categories`, `post_tags` |
| Catalog | `offerings`, `offering_revisions` (type: software/solution/service; loại `industry` đã bỏ ở migration `0011`) |

Quyết định thiết kế đáng nhớ:

- Một mô hình trang duy nhất (`pages` + `page_blocks`). `page_blocks.type` là text + Zod discriminated union, nên thêm block không cần migration.
- Header/footer/CTA đều là `menus` theo `location`.
- `redirects` chỉ nhận đường dẫn nội bộ bắt đầu bằng `/`, mã 301/308, thực thi trong `apps/website/src/proxy.ts`.
- `site_settings` giữ cấu hình xuất bản, liên kết ngoài và cửa sổ tư vấn tự hiện (`consult_popup`, CMS: Cấu trúc website › Cửa sổ tư vấn). Khi thêm key mới phải có default tương thích, và seed chỉ bổ sung key còn thiếu.
- **Mọi URL public là một Trang.** Trang hệ thống (`fixedWebsitePages` trong `pages.contract.ts`) có route do code giữ; CMS sửa nội dung, SEO, trạng thái nhưng không tạo/xóa/đổi slug. Trang danh sách (`kind: "listing"`: `/tin-tuc`, `/thiet-bi`, `/ho-tro/cai-dat`, `/phan-mem`, `/giai-phap`, `/dich-vu`) lấy phần đầu từ khối "Mở đầu" đầu tiên và SEO của trang; các khối còn lại hiển thị theo thứ tự, danh sách là khối `collection_list` (nguồn: bài viết, hướng dẫn, tệp cài đặt, thiết bị, phần mềm, giải pháp, dịch vụ) đặt được ở mọi trang. Trang danh sách thiếu khối danh sách thì route tự thêm danh sách mặc định (`defaultListingCollections`). `featured_posts`/`download_list` là loại cũ: vẫn đọc và render qua `collection_list`, CMS không cho thêm mới. Người có quyền `update`/`publish` của module sở hữu (`ownerModule`) sửa được trang danh sách của module đó. Key cũ `listing_content`/`catalog_content` chỉ còn là dự phòng tới khi chạy `pnpm db:backfill-listing-pages`.
- **Khối trang theo một hệ thống chung.** Mỗi khối có vỏ chung `appearance` (cột `page_blocks.appearance`: mã neo, nền `auto|white|tinted|dark|custom` — `custom` dùng `backgroundColor` #rrggbb, màu tối thì chữ trắng (`isDarkColor`), khoảng cách `auto|sm|md|lg`, `width` 40–100% độ rộng nội dung (`.block-width`, điện thoại rộng hết khung), ảnh nền `backgroundMediaId` phủ lớp màu nền `backgroundOverlay` %; CMS chỉnh ở `block-appearance-fields.tsx` có ô xem trước). Schema ở `shared/appearance.ts`; `sectionFrame()` (block-layout) tính khung cho một phần riêng lẻ — dùng cho phần đầu trang (chỉ ghi đè bằng màu tự chọn, ảnh nền, độ rộng) và 4 phần trang Sản phẩm (`offering content.appearance`). Thẻ con (thẻ lưới, gói giá, nhóm) có `background` tùy chọn, màu tối → `.card-on-dark`. CMS dùng `AppearanceEditor`/`ColorField` (`block-appearance-fields.tsx`, có ống hút EyeDropper). Trang Thiết bị dùng `sales_equipment.blocks` theo cùng schema và renderer. Khối `video` nhúng YouTube (`shared/youtube.ts`, khung `components/site/youtube-frame.tsx`); bài viết có node `youtube` trong nội dung soạn thảo. `resolveBlockFrames` (`pages/block-layout.ts`) quyết định nền/khoảng cách: "Tự động" xen kẽ trắng ↔ xanh nhạt với phần trước, nền tối chỉ cho khối có màu chữ riêng cho nền tối (số liệu, kêu gọi hành động, ảnh + chữ, quy trình, lưới thẻ, danh sách…; nền tối là xanh navy có hai vệt sáng góc, xem `tones` trong `components/ui/index.tsx`). Giao diện chỉ dùng token trong `apps/website/src/app/globals.css` (thang chữ `text-display/h2/h3/lead/body/small/caption`, màu `ink/muted/faint/line/subtle/brand-*/accent-*`, bo góc `rounded-card/rounded-control`) và component nền `components/ui` (`FrameSection`, `SectionHeading`, `CardTitle`, `CardText`, `IconTile`, `gridColumns`). Chỉ phần đầu trang chiếm cả màn hình. Biểu tượng khối: mã trong `shared/block-icons.ts`. **Lưới thẻ** (`features`; `industries`/`ecosystem` là thành phần cũ vẽ giống lưới thẻ): mỗi thẻ có `icon` và `mediaId` (ảnh) tùy chọn; `cardStyle` `compact` (mặc định, thẻ gọn biểu tượng nhỏ) hoặc `visual` (thẻ ảnh: ảnh ngang 16:10 sát mép thẻ, thẻ chưa có ảnh dùng mảng màu nhấn với biểu tượng lớn). `bento` (đúng 5 thẻ: thẻ đầu to bên trái chiếm hai hàng — ảnh lớn phía trên, tiêu đề `h3` cỡ lớn phía dưới; bốn thẻ ảnh nhỏ xếp hai cột bên phải; khác 5 thẻ thì tự về `visual`). Thẻ ảnh chưa có ảnh dùng mảng xanh thương hiệu nhạt + biểu tượng. Lưới thẻ trên nền tối và không có ảnh vẽ thành hai cột (tiêu đề trái, các ý 2 cột ngăn bằng vạch mảnh, không đóng khung). Hai phần liền nhau cùng nền (chọn tay) có vạch ngăn mảnh trong khung nội dung. Chỉ cần một thẻ có ảnh là cả lưới tự thành thẻ ảnh. `Card` có `flush` cho thẻ không đệm (đừng ghi đè `p-*` bằng class: thua trong CSS sinh ra). Trang chủ (`<main data-page="home">` trong `app/(web)/page.tsx`; bản xem trước CMS vẽ qua cùng route nên giống hệt): bố cục chuẩn nằm ở khối `[data-page="home"]` cuối `globals.css` — lề trái/phải và bề rộng khung giữ nguyên (`--container-max`, `--gutter`), đệm mỗi phần theo lựa chọn Khoảng cách của khối (`Section` gắn `data-space`: vừa 88/64/52px, gọn 56/48/40, rộng 112/80/64 cho máy tính/bảng/điện thoại), tiêu đề cách nội dung 40/36/32px, thẻ cách nhau 20px, hero 55/45 (`.hero-split`), lưới thẻ 4/2/1 cột (`data-card-grid`), gallery ảnh thích ứng 1–9 ảnh (`data-count`). Dải logo đối tác: dưới 8 logo là lưới ô cùng kích thước, số cột chia hết số logo (`logoGridClass`); từ 8 logo là dải chạy ngang (`.logo-marquee`).

| Nghiệp vụ | Nguồn dữ liệu | Route public |

- Editor CMS dùng form nghiệp vụ, không bắt người vận hành nhập JSON.
- `/admin/**` luôn `noindex`; `robots.txt` chặn `/admin/` và `/api/`.

## 3. Bảo mật

| Lớp | Cơ chế |
|---|---|
| Phiên đăng nhập | Token 32 byte ngẫu nhiên, DB chỉ lưu SHA-256; cookie `HttpOnly`, `SameSite=Lax`, `Secure` ở production, hạn 7 ngày |
| Chống dò mật khẩu | Quota PostgreSQL nguyên tử: 5 lần/15 phút theo username, 10 lần/15 phút theo IP; HTTP 429 kèm `Retry-After`; DB chỉ lưu HMAC |
| Độ dài mật khẩu CMS | Tự đổi mật khẩu: ≥ 10 ký tự (`ownPasswordMinLength`) và khác mật khẩu hiện tại. Quản trị viên đặt mật khẩu cho tài khoản khác ở Người dùng CMS: chỉ cần không rỗng và ≤ 1.024 ký tự (`cmsUserPasswordMinLength` = 1 trong `users.contract.ts`); mật khẩu ngắn hoặc yếu vẫn lưu được, form hiện thanh độ mạnh cảnh báo ngay khi gõ. Muốn siết lại thì tăng hằng số đó |
| Hồ sơ tài khoản | Panel "Tài khoản của tôi" (`AccountPanel`, trượt từ phải, mở từ menu tài khoản ở thanh trên; hai tab Hồ sơ và Mật khẩu; đường dẫn cũ `/admin/my-account` và `/admin/my-account/password` tự mở panel đúng tab rồi chuyển về `/admin`): người dùng tự sửa họ tên, email, số điện thoại (`PATCH /api/v1/admin/account/profile`) và ảnh đại diện (`POST`/`DELETE .../account/avatar`; chỉ PNG/JPEG/WebP ≤ 2 MB, nhận dạng theo nội dung). Nhóm `account` tự kiểm đăng nhập, không cần quyền Người dùng CMS hay Thư viện media; chỉ sửa được tài khoản của chính mình. Tên đăng nhập, vai trò, trạng thái vẫn do quản trị viên quản lý. Ảnh cũ chuyển vào hàng đợi xóa của thư viện media; mỗi thay đổi ghi nhật ký `user.update` kèm trước/sau |
| Chống request khác nguồn | `apps/api/src/proxy.ts`: mutation `/api/v1/admin/*` có `Origin` khác host public (theo `X-Forwarded-Host`) trả 403 |
| Phân quyền | RBAC `module.action` (`view/create/update/delete`, thêm `publish` cho nội dung xuất bản). Danh mục quyền là code (`permissions.ts`), seed đồng bộ vào DB; role là dữ liệu do admin tạo/sửa ở trang Vai trò, mỗi user một role. Kiểm tra 2 lớp: `apps/api/src/proxy.ts` theo module + method, route handler kiểm tra đúng hành động và `publish` (`lib/admin-access.ts`). Super Admin (`is_system`) không sửa/xóa được, luôn đủ quyền, không mất Super Admin cuối. Chống leo thang: chỉ cấp quyền mình có, không tự sửa role/khóa mình, chỉ Super Admin đụng tài khoản Super Admin. CMS dùng `useAdminPermissions().can()` chỉ để ẩn thao tác |
| Input | Zod strict ở mọi ranh giới; Drizzle tham số hóa truy vấn |
| Media | Kiểm magic bytes (PNG/JPEG/WebP/PDF/ZIP), tối đa 20 MB, object đã xóa mềm trả 404 |
| Lead | Honeypot; tối đa 3 liên hệ/15 phút cho mỗi IP đã băm (`leads.rate-limit.ts`), vượt thì HTTP 429 kèm `Retry-After` và thông báo nêu số phút chờ; khóa advisory chống request đồng thời |
| Giới hạn request chung | `apps/api/src/proxy.ts` đếm theo IP và nhóm đường dẫn trước khi chạm DB/S3 (kể cả trước khi kiểm phiên). Bảng hạn mức (mỗi phút, mỗi IP) nằm ở `apps/api/src/lib/rate-limit-policy.ts`: đăng nhập 20, liên hệ 20, tác vụ nhạy cảm (đổi mật khẩu/ảnh đại diện, khóa API, sao lưu) 20, tác vụ nặng (tải từ link, nhập Word, nhập/xuất bảng, xuất khách hàng, kiểm tra SEO) 20, tải tệp lên 60, ghi CMS 120, đọc CMS 600, `/media/*` 1.200, API public 120. Vượt thì HTTP 429 kèm `Retry-After` và `{ error: { code: "RATE_LIMITED" } }`; form đăng nhập của trình duyệt được chuyển về `/admin/login?error=RATE_LIMITED`. Lõi đếm ở `shared/rate-limit.ts` (cửa sổ cố định trong bộ nhớ, tối đa 20.000 khóa, bỏ khóa cũ nhất khi đầy, mỗi cửa sổ ghi đúng một dòng cảnh báo). Request **không có IP** (website và CMS gọi Backend từ phía server) không bị đếm. Đây chỉ là van xả lũ: quota đăng nhập và liên hệ ở PostgreSQL vẫn là lớp chính. Hạn chế đã biết: bộ đếm nằm trong tiến trình nên mất khi khởi động lại và nhân lên nếu chạy nhiều bản Backend. Chặn nhầm người dùng thật thì đặt `RATE_LIMIT_DISABLED=1` trong `.env.production` rồi `up -d` lại `api`. **Không có giới hạn cho trang HTML của website**: Caddy gốc không có rate limit (cần plugin `caddy-ratelimit`, phải tự build) và chặn theo IP dễ làm hại crawler hợp lệ; muốn có thì đặt CDN/WAF phía trước (xem hàng "IP client") |
| IP client | Lấy giá trị ngoài cùng bên phải của `X-Forwarded-For`. Đã kiểm chứng: Caddy ghi đè (không nối thêm) giá trị client gửi, nên gửi `X-Forwarded-For` giả không né được hạn mức; rewrite của Next (CMS/website → Backend) không nối thêm địa chỉ container. Nếu đặt CDN trước Caddy phải cấu hình `trusted_proxies`, nếu không mọi người dùng sẽ cùng một IP |
| Biên mạng | Chỉ Caddy mở 80/443. Header `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Strict-Transport-Security: max-age=31536000` (cố ý không `includeSubDomains`/`preload`), `Permissions-Policy` tắt camera/mic/vị trí/thanh toán/USB, CSP nền `base-uri 'self'; object-src 'none'` (CMS thêm `form-action 'self'`). Chưa có `script-src`: CSP theo nonce buộc mọi trang website render động và mất cache, nếu làm thì thử bằng `Content-Security-Policy-Report-Only` trước. Domain public chỉ nhận body ≤ 128 KB (liên hệ, sự kiện thống kê); tải tệp lên chỉ có ở domain CMS (≤ 21 MB). 3 app Next tắt `X-Powered-By` (`poweredByHeader: false`) và chạy với `cap_drop: ALL` + `no-new-privileges`. `/api/internal/*` trả 404 ở Caddy. S3 nằm ở network `storage` nội bộ, chỉ Backend truy cập |
| Secret | `.env*` không được commit. Compose dùng `${VAR:?missing}` nên thiếu secret thì stack không khởi động |

## 4. Vận hành

### Local

```sh
docker compose up -d          # PostgreSQL 127.0.0.1:5433, S3Mock 127.0.0.1:9090
pnpm db:migrate && pnpm db:seed:cms
pnpm dev:api              # 3002
pnpm dev:admin                  # 3001
pnpm dev                      # 3000
```

- Windows: `pnpm dev:all` (`scripts/dev.ps1`) làm các bước trên trừ migrate/seed: bật Docker Desktop nếu đang tắt, chạy `db` + `storage` và chờ healthy, mở 3 app trong 3 tab Windows Terminal (không có thì 3 cửa sổ PowerShell), bỏ qua app đã chạy sẵn. Tùy chọn `-Analytics` (thêm Umami), `-NoDocker`. `pnpm dev:stop` dừng 3 app và container (giữ volume). Script dừng ngay nếu thiếu `.env`, để Compose không tạo lại container `db` với biến rỗng.
- Cấu hình nằm ở `.env` gốc repo (mẫu: `.env.example`). Nếu `tsx` báo `spawn UNKNOWN` trên Windows, chạy `node --import tsx scripts/<file>.ts`.
- `pnpm db:import:v1-content` nhập lại nội dung V1. Mọi script seed/import đều idempotent và không ghi đè nội dung đã sửa trong CMS.

### Production (VPS + Docker Compose)

Dịch vụ: `proxy` (Caddy), `website`, `admin`, `api`, `db` (PostgreSQL 17), `s3` (SeaweedFS một node), `umami` (thống kê truy cập, database `umami` riêng trên cùng PostgreSQL), cùng các job chạy một lần `migrate`, `seed-admin`, `umami-db-init`. Image nền được ghim digest.

1. Trỏ DNS `SITE_ADDRESS`, `ADMIN_SITE_ADDRESS` và `ANALYTICS_SITE_ADDRESS` về VPS, mở cổng 80/443.
2. `cp .env.production.example .env.production && chmod 600 .env.production`, rồi thay mọi giá trị `replace_with_...`.
3. `docker compose --env-file .env.production -f compose.production.yaml up -d --build`
4. Kiểm tra `logs seed-admin`. Job này tạo hoặc nâng quyền tài khoản `INITIAL_ADMIN_*`, không ghi đè mật khẩu đã có.
5. Nội dung nền (trang chủ, trang hệ thống, menu, cấu hình, bài viết, catalog, thiết bị): DB mới chưa có. Nạp `scripts/data/base-content.sql` (sinh bởi `sh scripts/export-base-data.sh` từ DB local, không gồm log, lịch sử phiên bản, tài khoản; chạy sau `seed-admin`, khi bảng nội dung còn trống): `... exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < scripts/data/base-content.sql`. Media chỉ có metadata, tệp thật chép bằng `scripts/backup-media.mjs`. Hoặc chạy các seed `pnpm db:seed:cms`. Xóa nhật ký và lịch sử phiên bản của DB local: `CONFIRM=yes sh scripts/purge-history.sh` (không khôi phục được).
6. Kiểm tra storage: `... run --rm migrate node scripts/audit-s3-storage.mjs`
7. Thống kê: mở `ANALYTICS_SITE_ADDRESS`, đăng nhập `admin`/`umami` và **đổi mật khẩu ngay**, thêm website (domain = `SITE_ADDRESS`), tạo API key; điền `UMAMI_WEBSITE_ID`, `UMAMI_API_KEY` vào `.env.production` rồi chạy lại lệnh `up -d`. Chưa điền thì website không chèn script và CMS báo "chưa kết nối".

Cập nhật: `git pull --ff-only`, rồi chạy lại lệnh `up -d --build`. Migration chạy trước khi thay container; nếu release không lên, xem `logs migrate`.

Tác vụ định kỳ (lên lịch ở host, chạy qua image migration):

| Lệnh | Tần suất | Ghi chú |
|---|---|---|
| `pnpm db:cleanup-login-throttles` | Hằng ngày | Tối đa 500 bucket hết hạn mỗi lần |
| `pnpm db:cleanup-media` | Thủ công | Media xóa mềm quá 7 ngày, bỏ qua tệp còn được tham chiếu. Chưa lên lịch, chờ chốt policy |

Sao lưu (`scripts/backup.sh`, chạy trên host ở thư mục repo):

- Mỗi lần chạy: `pg_dump -Fc` database iOrder và `umami` (nếu có) vào `BACKUP_DIR/db/<thời điểm UTC>/` kèm `SHA256SUMS`; khôi phục thử bản iOrder vào database tạm `iorder_restore_check` rồi xóa (lỗi hoặc không có dữ liệu → script dừng, bản đó không được giữ); sao lưu media theo từng object qua S3 API vào `BACKUP_DIR/media/` (service `backup-media`, profile `ops`). Media chỉ thêm, không xóa, nên dump cũ vẫn tìm được tệp đã dọn khỏi S3.
- Mặc định `BACKUP_DIR=/var/backups/iorder`, giữ `BACKUP_KEEP=14` bản database. Có khóa `flock`, không chạy chồng.
- Lên lịch: `30 2 * * * cd /srv/iorder && scripts/backup.sh >> /var/log/iorder-backup.log 2>&1`.
- Bản sao lưu nằm cùng VPS chỉ chống lỗi thao tác/dữ liệu, không chống mất máy: phải chép `BACKUP_DIR` ra nơi khác (máy khác hoặc object storage ngoài).
- Trạng thái: cuối mỗi lần chạy, script/CMS ghi `system.backup.success`/`system.backup.failure` (lần gần nhất) và nối thêm vào `system.backup.history` (30 lần gần nhất, mới nhất trước, gồm cả thư mục sao lưu, thư mục repo và tên database đã dump) vào `site_settings` (script qua `scripts/backup-status.sql`, CMS trực tiếp bằng Drizzle — `server/backup/backup-status.ts`, cùng giới hạn). CMS đọc trạng thái này, chỉ người có `settings.view`: thẻ "Sao lưu" ở Tổng quan (link "Chi tiết") và mục trong chuông thông báo khi lỗi hoặc quá 36 giờ chưa có bản mới. Script lỗi trước khi kết nối được database thì không ghi được lỗi, nhưng thẻ vẫn chuyển "Quá hạn" sau 36 giờ.

Trang `/admin/backup` ("Sao lưu & phục hồi" trong nhóm Hệ thống; chỉ Super Admin thao tác, người khác có `settings.view` chỉ xem lịch sử):

- **Một cú bấm trên máy Windows đang chạy** (`server/backup/local-ops.ts`, gọi từ `POST /api/v1/admin/backup`, không cần PowerShell hay biết Docker): "Sao lưu ngay" — dump qua `docker compose exec db` (stdin/stdout nối thẳng tệp, không qua `/tmp` + `docker compose cp` như script), khôi phục thử, sao lưu media, dọn bản cũ, ghi trạng thái; "Phục hồi" — tự sao lưu dữ liệu hiện tại trước (không bỏ qua được), phục hồi thử bản chọn vào database tạm để chắc dùng được, rồi mới `dropdb`/`createdb`/`pg_restore` đè lên database thật và đưa lại media còn thiếu; "Bật/tắt tự động sao lưu mỗi đêm 21:00" đăng ký thẳng vào Task Scheduler bằng `schtasks.exe` (không cần quyền quản trị), tác vụ chạy `scripts/backup.ps1` nên vẫn chạy được khi không ai mở CMS.
- `site_settings` (nên cả lịch sử sao lưu) nằm trong chính database bị phục hồi: `pg_restore` sẽ viết đè nó về đúng như lúc tạo bản đang phục hồi. `snapshotBackupBookkeeping`/`restoreBackupBookkeeping` chụp lại ba khóa trước khi đụng tới database thật rồi ghi đè lại sau, để lịch sử không "lùi về quá khứ"; `recordBackupRestoreEvent` thêm một dòng "Đã phục hồi" (nguồn gốc `fromStamp`) vào lịch sử. Phục hồi lỗi SAU KHI đã xóa database cũ sẽ tự khôi phục khẩn cấp lại bản sao lưu an toàn vừa tạo, để CMS không rơi vào trạng thái không đọc được gì.
- `GET`/`POST /api/v1/admin/backup` không map permission module nào (Super Admin). Thao tác tay (không phải lịch tự động) được ghi vào `audit_logs` (`backup.run`/`backup.restore`, xem Nhật ký hoạt động) — `audit_logs` cũng nằm trong database bị phục hồi nên không được bảo vệ như `site_settings`, chỉ để tiện xem chứ không phải nguồn sự thật chính.
- **Máy chủ thật (VPS, chưa triển khai):** CMS không tự phục hồi hay lên lịch được từ xa; trang hiện các lệnh thủ công tương ứng (`lib/backup-commands.ts`, chỉ sinh lệnh để chép, không chạy gì).

Sao lưu trên máy Windows (dev local): `pnpm backup:local` (`scripts/backup.ps1`) làm đúng các bước trên với container `db`/`storage` của `compose.yaml` (dump trong container rồi `docker compose cp`, không qua pipeline PowerShell vì làm hỏng dữ liệu nhị phân). Mặc định ghi vào `..\iorder-backups\db` và `..\iorder-backups\media` cạnh thư mục repo, giữ 14 bản; tùy chọn `-BackupDir`, `-Keep`, `-NoVerify`, `-NoMedia`, `-EnvFile`. Tệp khác trong thư mục sao lưu không bị đụng tới. Muốn chạy hằng ngày thì tạo Task Scheduler gọi lệnh trên (trang `/admin/backup` có sẵn lệnh `schtasks`).

Khôi phục (phá hủy dữ liệu hiện tại, chỉ làm khi cần):

1. Dừng ứng dụng: `... stop api admin website`.
2. Database: `... exec -T db sh -c 'dropdb -U "$POSTGRES_USER" "$POSTGRES_DB" && createdb -U "$POSTGRES_USER" "$POSTGRES_DB" && pg_restore -U "$POSTGRES_USER" --no-owner --exit-on-error -d "$POSTGRES_DB"' < BACKUP_DIR/db/<bản>/iorder_v2.dump` (thay tên tệp theo `POSTGRES_DB`).
3. Media: `... run --rm --no-deps -v BACKUP_DIR/media:/backup/media backup-media node scripts/backup-media.mjs restore /backup/media` (chỉ đưa lên object còn thiếu, không ghi đè).
4. `... up -d`, rồi kiểm tra website, đăng nhập CMS, mở vài ảnh.

Chuyển dữ liệu từ MinIO cũ: volume `seaweed-data` là volume mới. Nếu production đã có media thì phải sao chép object và đối soát với `storage_key` trước khi cutover, đồng thời giữ volume cũ cho đến khi restore đạt.

### Log và theo dõi

- **Mã request:** Caddy gắn `X-Request-Id` (UUID, thay giá trị client tự gửi) cho mọi request và trả lại trong response. CMS chuyển tiếp mã khi gọi Backend; proxy Backend nhận hoặc tạo mới cho `/api/*`, `/media/*`. Người dùng báo lỗi kèm mã này (DevTools → Network → header `x-request-id`) là tìm được đúng dòng log ở cả 3 tầng.
- **Access log:** Caddy ghi JSON mỗi request (trạng thái, `duration`, IP, user agent, `uuid` = mã request). Cookie/Authorization bị che, tham số `query` (từ khóa tìm kiếm) bị bỏ khỏi URI.
- **Log ứng dụng:** `logger` trong `packages/shared/src/server/shared/logger.ts`. Production in một dòng JSON: `time`, `level`, `service`, `msg`, `requestId`, `method`, `path` (không query string), trường bổ sung, `err` (name, message, 12 frame stack, mã lỗi Postgres, chuỗi `cause`). Không ghi giá trị khóa nhạy cảm (password, token, cookie, hash, session…) và tham số SQL. Dev in dạng dễ đọc. `LOG_LEVEL` (debug/info/warn/error), `LOG_FORMAT=json` để ép JSON.
- **Lỗi chưa xử lý:** `src/instrumentation.ts` (`onRequestError`) của cả 3 app ghi kèm route và requestId. Từ chối quyền (403) và mutation khác nguồn ghi mức `warn` kèm người thao tác.
- **Giữ log:** Docker `json-file` xoay vòng 5 × 20 MB mỗi container.

Lệnh hay dùng (`dc` = `docker compose --env-file .env.production -f compose.production.yaml`):

| Mục đích | Lệnh |
|---|---|
| Theo dõi lỗi trực tiếp | `dc logs -f --no-log-prefix api admin website | grep '"level":"error"'` |
| Tìm theo mã request | `dc logs --no-log-prefix --since 24h | grep <mã>` |
| Request chậm hơn 2 giây | `dc logs --no-log-prefix proxy | jq -c 'select(.duration > 2) | {uuid, status, duration, uri: .request.uri}'` |
| Đếm lỗi 5xx theo đường dẫn | `dc logs --no-log-prefix --since 24h proxy | jq -r 'select(.status >= 500) | .request.uri' | sort | uniq -c` |

Chưa có: cảnh báo tự động khi healthcheck lỗi hoặc lỗi tăng đột biến (cần chọn kênh nhận: email/Zalo/dịch vụ uptime).

### Kết nối & khóa API nhập ở CMS (mã hóa)

- **Trung tâm biến kết nối theo công cụ:** màn chia thành **thẻ theo từng công cụ ngoài**, mỗi thẻ gồm nhiều biến (địa chỉ, mã, khóa) và ghi "x/y biến đã đặt". Hiện có **Umami** (`umami_api_url`, `umami_website_id`, `umami_api_key`) và **Google Search Console** (`google_service_account`, `search_console_property`). Mỗi thẻ chỉ tóm tắt (từng biến: giá trị không bí mật hoặc gợi ý, đã đặt hay chưa) và có **một nút Cấu hình**: bấm thì mở **một panel trượt bên phải** (`AdminSidePanel`) chứa **tất cả biến của công cụ đó**, một ô mật khẩu xác nhận và một nút Lưu (thanh nút dính đáy panel). Chỉ biến đã sửa được gửi (khóa bí mật để trống = giữ nguyên; hộp “Xóa khỏi CMS” cho biến đã lưu); `PUT /api/v1/admin/secrets` nhận `{ items: [{ key, value, expectedVersion }], password }` và kiểm tra hết rồi mới ghi, một biến sai thì không biến nào được lưu và lỗi nêu đúng biến. Esc hoặc bấm nền để đóng, giá trị và mật khẩu trong biểu mẫu bị xóa khi đóng. “Tạo khóa chủ” cũng mở trong panel riêng. Địa chỉ và mã không bí mật (`exposeValue`) nên hiển thị lại được; khóa bí mật chỉ ghi. **Thêm công cụ mới** = thêm khóa vào `secretKeys` + `secretMetas` (nhãn, mô tả, tên biến môi trường tương ứng) + bộ kiểm tra ở `secrets.catalog.ts` + một dòng ở `integrationTools` (`secrets.contract.ts`), rồi cho dịch vụ cần dùng đọc qua `getCmsSecret(key)` sau khi kiểm biến môi trường; giao diện tự hiện thẻ mới. Đây là biến **kết nối** (CMS gọi ra công cụ ngoài), không phải webhook sự kiện.
- **Umami đọc từ CMS ở đâu:** Tổng quan (`analytics.service.ts`) lấy từng biến từ môi trường trước, thiếu mới hỏi CMS; màn Tình trạng hệ thống tính cả biến lưu ở CMS. Mã website còn đi vào website công khai: Backend trả `integrations.umamiWebsiteId` trong `/api/v1/public/content?resource=shared` (môi trường `UMAMI_WEBSITE_ID` thắng, không có thì lấy ở CMS) và `apps/website/src/app/layout.tsx` gắn thẻ theo dõi từ đó, nên đổi ở CMS có hiệu lực trong khoảng một phút (cache nội dung 60 giây). **Đường chuyển tiếp `/stats/*` vẫn do hạ tầng đảm nhiệm** (Caddy ở production, `UMAMI_URL` trong `next.config.ts` khi chạy local) và không đổi được ở CMS; địa chỉ Umami ở CMS chỉ để Backend gọi API.
- **Màn:** CMS → Hệ thống → **Kết nối & khóa API** (`/admin/integrations`), **chỉ Super Admin** (menu ẩn với người khác, trang chuyển sang "Không có quyền", API trả 403 và proxy không map permission nào cho `/api/v1/admin/secrets`). Nhập được: khóa tài khoản dịch vụ Google (chọn tệp JSON, không gõ JSON), thuộc tính Search Console, API key Umami. Người vận hành không phải sửa tệp `.env` hay đăng nhập máy chủ để đổi các khóa này.
- **Lưu trữ:** bảng `secure_settings` (migration 0025). Mỗi giá trị mã hóa AES-256-GCM (`v1.nonce.tag.bảnmã`, nonce 96-bit ngẫu nhiên, tên khóa ràng vào dữ liệu xác thực nên không hoán đổi được giữa hai khóa). **Khóa chủ nằm ngoài database** và lấy từ một trong hai nơi: biến môi trường `SECRETS_MASTER_KEY` (base64 của đúng 32 byte, tạo bằng `openssl rand -base64 32`; thắng) hoặc **tệp khóa chủ** `SECRETS_KEY_FILE` (mặc định `apps/api/.data/secrets-master.key` khi chạy local, `.gitignore` đã chặn; production `/data/secrets/master.key` trong volume bền `secrets-data`). Chưa có khóa chủ thì Super Admin bấm **“Tạo khóa chủ”** ở CMS (nhập lại mật khẩu): Backend tự sinh 32 byte ngẫu nhiên, ghi tệp quyền 0600 bằng cờ `wx` (không bao giờ ghi đè khóa đã có, kể cả tệp hỏng), dùng được ngay không cần khởi động lại và không trả khóa chủ cho ai; việc tạo được ghi vào Nhật ký hoạt động (`secret.master_key_created`). Sai định dạng hoặc không đọc được thì màn báo rõ, không cho tạo đè; các biến môi trường cũ vẫn dùng bình thường.
- **Chỉ ghi, không đọc lại:** không có API hay màn nào trả giá trị khóa. Màn chỉ hiện "đã đặt/chưa đặt", nguồn đang dùng, gợi ý không bí mật (email tài khoản dịch vụ; bốn ký tự cuối của API key; thuộc tính Search Console không bí mật nên hiện nguyên giá trị), ai và lúc nào cập nhật. Muốn đổi thì nhập khóa mới (kèm version để chống ghi đè đồng thời, HTTP 409).
- **Xác nhận bằng mật khẩu:** đặt, thay và xóa đều phải nhập lại **mật khẩu của chính người đang đăng nhập** (`verifyPassword`). Sai 5 lần trong 15 phút thì bị chặn tạm (HTTP 429, bộ đếm nằm trong bộ nhớ tiến trình Backend nên khởi động lại là xóa; chấp nhận được vì chỉ Super Admin có quyền và mọi lần sai đều ghi nhật ký). Chưa có xác thực hai lớp (2FA): làm sau.
- **Nhật ký hoạt động:** `secret.set`, `secret.clear`, `secret.reauth_failed` chỉ ghi tên khóa và đã đặt hay chưa, **không bao giờ ghi giá trị hay gợi ý**.
- **Biến môi trường luôn thắng:** nếu máy chủ đã đặt `GOOGLE_SERVICE_ACCOUNT_JSON`/`_FILE`, `SEARCH_CONSOLE_PROPERTY` hay `UMAMI_API_KEY` thì giá trị đó được dùng, giá trị ở CMS (nếu có) được giữ nhưng chưa có hiệu lực và màn nói rõ để khỏi nhầm. Dịch vụ đọc khóa ở CMS lúc dùng (bộ nhớ đệm 30 giây, đổi khóa thì xóa ngay; Search Console xóa số liệu đã nhớ khi khóa hoặc thuộc tính đổi), nên đổi khóa không cần khởi động lại.
- **Không chuyển được sang CMS** (phải ở env): `DATABASE_URL`/`POSTGRES_*`, `S3_*`, `INITIAL_ADMIN_*`, `PUBLISH_WEB_REVALIDATE_SECRET` (website không truy cập database), `LEAD_IP_HASH_SALT` và `UMAMI_APP_SECRET`/`UMAMI_TWO_FACTOR_ENCRYPTION_KEY` (đổi là hỏng dữ liệu đã băm/mã hóa), `INDEXNOW_KEY` (website cũng cần), mã website và địa chỉ của Umami (website cần).
- **Sao lưu và khóa chủ:** bản sao lưu database chứa bản mã hóa và **không** chứa khóa chủ; **mất khóa chủ là mất toàn bộ giá trị** (phải nhập lại). Sao lưu khóa chủ RIÊNG ngoài sao lưu database: giá trị `SECRETS_MASTER_KEY` vào trình quản lý mật khẩu, hoặc tệp trong volume `secrets-data` (script `backup.sh` chỉ sao lưu database và media, không gồm volume này). Tệp khóa chủ cùng máy với Backend nên bảo vệ ngang với `.env`: ai đọc được máy chủ thì đọc được nó, nhưng bản dump database một mình thì vô dụng. Đổi khóa chủ thì các khóa đã lưu không giải mã được: dịch vụ coi như chưa cấu hình, Backend ghi cảnh báo và Super Admin nhập lại. Chưa có chức năng xoay khóa chủ tự động.
- **Mã nguồn:** `packages/shared/src/server/secrets/` (`secrets.crypto.ts`, `secrets.catalog.ts` kiểm tra và chuẩn hóa từng loại khóa, `secrets.service.ts` quy tắc, `secrets.repository.ts` Drizzle, `secrets.contract.ts` kiểu và schema dùng chung với trình duyệt), `apps/api/.../admin/secrets/route.ts` (GET, PUT, DELETE; `Cache-Control: no-store`), `components/admin/integration-secrets-panel.tsx`. Thêm khóa mới: thêm vào `secretKeys`, `secretMetas` và bộ chuẩn hóa trong `secrets.catalog.ts`, rồi cho dịch vụ dùng nó đọc qua `getCmsSecret`.
- **Mật khẩu mặc định theo quy ước** `<tên>.iOrder@2026` (ví dụ `admin.iOrder@2026`, `postgres.iOrder@2026`) trong `.env.example` và `.env.production.example`, chỉ áp cho **mật khẩu đăng nhập** (tài khoản CMS đầu tiên và PostgreSQL), không áp cho khóa mật mã như `LEAD_IP_HASH_SALT`, `PUBLISH_WEB_REVALIDATE_SECRET`, `UMAMI_*`, `S3_*`, `SECRETS_MASTER_KEY` vì đoán được thì chữ ký và mã hóa mất tác dụng. Đây là mật khẩu **đoán được** (có trong repo): CMS nằm trên Internet nên phải đổi ngay sau lần đăng nhập đầu (Tài khoản của tôi → Mật khẩu) và đổi mật khẩu PostgreSQL trước khi mở máy chủ ra ngoài. Mật khẩu có `@` dùng được trong `DATABASE_URL` (viết `%40` khi gõ tay; compose ghép thẳng và Node/`postgres.js` đọc đúng). Đổi `POSTGRES_PASSWORD` trong `.env` không đổi mật khẩu của database đã tạo sẵn (volume Docker giữ mật khẩu lúc khởi tạo).

### Tình trạng hệ thống và vai trò Vận hành

- **Màn:** CMS → Hệ thống → **Tình trạng hệ thống** (`/admin/system`, quyền `system.view`). Một chỗ cho người vận hành thấy: database (phản hồi, phiên bản, dung lượng, số kết nối), migration (đã áp dụng so với số migration trong mã nguồn), kho tệp S3, website (Backend gọi `/api/health` của website theo địa chỉ trong `PUBLISH_WEB_REVALIDATE_URL`), Umami, Google Search Console, máy chủ (ổ đĩa, RAM, tải CPU, thời gian chạy, Node), sao lưu (kèm liên kết sang Sao lưu & phục hồi), tác vụ định kỳ và danh sách cấu hình đã đặt hay chưa. Khung đầu trang nêu từng mục cần chú ý hoặc lỗi; trang tự làm mới mỗi phút khi tab đang mở.
- **Ngưỡng:** database chậm hơn 1 giây hoặc dùng từ 80% kết nối → cần chú ý; ổ đĩa còn dưới 15% → cần chú ý, dưới 5% → lỗi; RAM khả dụng dưới 7% → cần chú ý; sao lưu quá 36 giờ hoặc chưa có → cần chú ý, lần gần nhất lỗi → lỗi. Database, kho tệp, website hỏng → lỗi. Umami và Search Console chưa nối là trung tính (không bắt buộc), đang lỗi chỉ là cần chú ý. Production thiếu khóa làm mới website, địa chỉ làm mới website hoặc địa chỉ website chính thức → cần chú ý.
- **Tác vụ định kỳ:** `pnpm db:cleanup-login-throttles` (hằng ngày; quá 36 giờ chưa chạy thì cần chú ý), `db:cleanup-media` và `db:cleanup-content --apply` (chạy tay, không bao giờ quá hạn) ghi lần chạy gần nhất vào `site_settings` (key `system.job.<tên>`, JSONB có schema `jobRunSchema`) qua `recordJobRun`; lỗi khi ghi không làm hỏng tác vụ. Thêm tác vụ mới: thêm tên vào `systemJobNames` và `systemJobDefinitions`.
- **Phiên bản:** Backend hiện `APP_COMMIT` nếu có (chuỗi ngắn an toàn). Đặt khi triển khai bằng cách thêm biến này trước lệnh `docker compose ... up -d --build`, giá trị lấy từ `git rev-parse --short HEAD` (đã nối vào `compose.production.yaml`; không đặt thì hiện trống).
- **Mã nguồn:** `packages/shared/src/server/system/` (`system-status.service.ts`: mọi kiểm tra chạy song song, mỗi kiểm tra có giới hạn 5 giây, nhớ kết quả 5 giây và gộp lần gọi cùng lúc; `system-status.ts`: nối với database, S3, Umami, Search Console và máy chủ thật; `job-runs.ts`), endpoint `GET /api/v1/admin/system-status` (chỉ GET), màn `components/admin/system-status-panel.tsx`.
- **Bảo mật:** phản hồi chỉ có số đo và nhãn; không có giá trị biến môi trường, chuỗi kết nối, khóa hay mã truy cập (cấu hình chỉ báo "đã đặt/chưa đặt"); lỗi kỹ thuật chỉ ghi log phía máy chủ, người dùng thấy câu giải thích chung (có test).
- **Vai trò Vận hành hệ thống** (`sysops`, mặc định): chỉ có bốn quyền xem: Tổng quan, Cài đặt website, Nhật ký hoạt động, Tình trạng hệ thống. Thấy màn Tình trạng hệ thống, Sao lưu & phục hồi (xem lịch sử) và Nhật ký hoạt động; **không** sửa nội dung, không quản lý người dùng hay vai trò, không chạy/phục hồi sao lưu (vẫn chỉ Super Admin). Chỉ Super Admin và `sysops` có `system.view` mặc định (vai trò Phân tích cố ý không có). Vai trò mặc định mới được tạo ở lần chạy `seed-admin` kế tiếp (`syncCmsPermissionCatalog`); vai trò có sẵn không tự nhận quyền mới, Super Admin tick ở Người dùng & vai trò.

### Giữ CMS gọn nhẹ (tối ưu cho VPS)

- **Số đo bản build production của CMS** (19/11/2026, `next build` vào thư mục riêng qua `NEXT_DIST_DIR`, không đụng `.next` của `next dev`): trang thường (Bảng điều khiển, danh sách, Sao lưu, Giao diện) tải khoảng **140–160 KB gzip JS**, trong đó ~89 KB là React/Next dùng chung; trang soạn bài **~342 KB gzip** vì Tiptap/ProseMirror (~151 KB) chỉ nạp ở màn soạn thảo; trang đăng nhập **~22 KB gzip**. CSS toàn cục **~39 KB gzip** (227 KB gốc). Kiểm lại sau mỗi lần thêm thư viện lớn.
- **Font:** chỉ Inter (mặc định) được nạp trước (2 tệp, ~57 KB). Manrope, DM Sans, Plus Jakarta Sans để `preload: false` ở `app/layout.tsx`: CSS vẫn khai báo `@font-face` nhưng tệp font chỉ tải khi người vận hành chọn font đó ở Giao diện CMS. Trước đó mọi lần mở CMS đều nạp trước cả 8 tệp (~175 KB).
- **Trang trí Giáng sinh:** `christmas-decor-lazy.tsx` chỉ tải gói trang trí (cây thông, chuông, tuyết, ~2 KB gzip) khi theme là Giáng sinh; các theme khác không tải và không chạy mã này.
- **Container CMS (`compose.production.yaml`):** `mem_limit` 384 MB, `cpus` 1, `NODE_OPTIONS=--max-old-space-size=256`, chỉnh bằng `ADMIN_MEM_LIMIT`, `ADMIN_CPUS`, `ADMIN_HEAP_MB`. **Chưa đo trên VPS thật**: nếu container bị khởi động lại vì thiếu bộ nhớ (`docker inspect --format '{{.State.OOMKilled}}'`) thì tăng.
- **Tự gọi lại API:** CMS gần như không polling (chỉ màn Tình trạng hệ thống mỗi phút khi tab đang mở, và thanh tiến trình tải); Search Console và Umami được Backend nhớ nhiều giờ, nên không thêm tải đều đặn lên VPS.
- **Chưa làm (cần quyết định):** tách `christmas-login.css` (~6 KB gzip) khỏi CSS toàn cục (dùng chung với theme Giáng sinh trong khung CMS nên phải tách cẩn thận); bỏ `@aws-sdk/client-s3`, `drizzle-orm`, `postgres` khỏi `apps/admin/package.json` (mã CMS không import trực tiếp; chỉ giảm dung lượng cài đặt khi build, không đổi image chạy, cần cập nhật lockfile); rút số font/theme nếu muốn nhẹ hơn nữa.

### Xem trước bản nháp

- Trình soạn thảo trang, bài viết, sản phẩm/giải pháp/dịch vụ có nút "Xem trước bản nháp" khi nội dung chưa xuất bản. Website hiện **bản đã lưu** (không phải bản đang gõ dở) kèm thanh vàng "Đang xem bản nháp" và `noindex`.
- Liên kết hết hạn sau 1 giờ và chỉ mở đúng nội dung được cấp. Người không có liên kết vẫn thấy 404 như trước.
- Khóa ký: `PREVIEW_SECRET` nếu đặt, nếu không thì suy ra từ `PUBLISH_WEB_REVALIDATE_SECRET` (production bắt buộc có một trong hai). Đổi khóa làm mọi liên kết cũ mất hiệu lực.

### Ảnh chia sẻ tự sinh (/og)

- Thứ tự ảnh Open Graph/Twitter (`apps/website/src/lib/page-metadata.ts`): ảnh riêng của nội dung (SEO nâng cao hoặc ảnh bìa) → ảnh chia sẻ mặc định trong Cài đặt xuất bản → ảnh tự sinh `/og?title=…&sig=…` (1200×630, tên trang trên nền thương hiệu, tên miền ở chân). Cần `siteUrl` (metadataBase) mới tạo.
- Địa chỉ `/og` được ký HMAC theo tiêu đề (`PREVIEW_SECRET`, hoặc `PUBLISH_WEB_REVALIDATE_SECRET`); chữ ký sai trả 404 nên không ai dùng được để tạo ảnh có chữ tùy ý trên domain. Đổi khóa thì ảnh cũ trong bộ nhớ đệm của Facebook/Zalo vẫn còn, ảnh mới dùng chữ ký mới.
- Font: `apps/website/public/fonts/BeVietnamPro-Bold.ttf` (OFL, kèm giấy phép), đọc bằng `process.cwd()/public/fonts` nên chạy được cả trong image Docker. Giới hạn bundle của ImageResponse là 500KB.

### Tự báo công cụ tìm kiếm (IndexNow)

- Tự bật, không cần cấu hình: khóa sinh từ `PUBLISH_WEB_REVALIDATE_SECRET` (HMAC một chiều, `resolveIndexNowKey`) nên `api` và `website` luôn ra cùng khóa. Website phục vụ khóa tại `/indexnow.txt`, backend tự báo `api.indexnow.org` (Bing, Yandex…). `INDEXNOW_KEY` để tự đặt khóa, `INDEXNOW_DISABLED=true` để tắt hẳn.
- Luồng: mutation admin gọi `revalidatePath` (`apps/api/src/lib/publish-cache-revalidation.ts`) → gom các đường dẫn cụ thể → website làm mới cache xong → `apps/api/src/lib/indexnow.ts` đọc `/sitemap.xml` và chỉ báo URL vừa đổi mà có trong sitemap. Nhờ vậy bản nháp, trang `noindex` và trang chưa xuất bản không bị gửi. Mỗi URL tối đa một lần mỗi 10 phút.
- Không gọi ra ngoài khi: tắt hoặc không có secret/khóa hợp lệ, thiếu `siteUrl` trong Cài đặt xuất bản, tắt "cho phép công cụ tìm kiếm", hoặc địa chỉ là localhost/mạng nội bộ. Lỗi chỉ ghi log, không chặn lưu nội dung. Google không dùng IndexNow; với Google vẫn dựa vào sitemap và Search Console.

### Khám phá nội dung, thẻ robots và dữ liệu cấu trúc

- **`/llms.txt`** (`apps/website/src/app/llms.txt/route.ts`, dựng bằng `lib/llms-txt.ts`): mục lục Markdown cho công cụ AI theo llmstxt.org: giới thiệu, thông tin liên hệ, rồi liên kết kèm mô tả tới trang, sản phẩm/giải pháp/dịch vụ, thiết bị (có giá), hướng dẫn, tin mới, kênh chính thức; trang pháp lý, sitemap và RSS nằm ở mục `Optional`. Cùng điều kiện với sitemap: cần `siteUrl`, tôn trọng "cho phép công cụ tìm kiếm" và bỏ nội dung noindex/ẩn khỏi sơ đồ (`isSitemapEligible`); không thì trả 404. Google không hỗ trợ tệp này (Google nói AI Overviews/AI Mode dùng chung chỉ mục và hệ thống xếp hạng với tìm kiếm thường); bằng chứng nó giúp được trích dẫn bởi các công cụ AI khác còn yếu và các nguồn mâu thuẫn nhau, rõ nhất là công cụ lập trình đọc tài liệu. Giữ vì chi phí gần bằng 0, không coi là đòn bẩy SEO.
- **`/feed.xml`** (`app/feed.xml/route.ts`, `lib/rss.ts`): RSS 2.0 cho tin tức (30 bài mới nhất, không gồm hướng dẫn), cùng điều kiện như trên. Liên kết tự khám phá `<link rel="alternate" type="application/rss+xml">` đặt ở layout và được `contentMetadata` kế thừa (alternates của trang thay toàn bộ alternates của layout nên phải chuyển tiếp `types`).
- **`/manifest.webmanifest`** (`app/manifest.ts`): tên, màu thanh địa chỉ, biểu tượng; `display: browser` vì đây là website giới thiệu, không phải ứng dụng cài đặt.
- **Thẻ robots** (`lib/robots-meta.ts`, dùng ở layout và `contentMetadata`): trang cho lập chỉ mục thêm `googlebot: max-image-preview:large, max-snippet:-1, max-video-preview:-1` để Google được hiện ảnh lớn và đoạn trích dài; trang nháp/xem trước/noindex chỉ giữ `index, follow`.
- **JSON-LD tự động** (`lib/structured-data.ts`, `components/site/content-json-ld.tsx`): mỗi trang có nút `WebPage` thuộc `WebSite` chung (`isPartOf`), kèm `dateModified` (từ `updatedAt` của trang công khai); `AboutPage` (Giới thiệu), `ContactPage` (Liên hệ), `CollectionPage` (trang danh sách). Khối FAQ đang bật (trang, trang chủ, thiết bị) và câu hỏi của sản phẩm/giải pháp/dịch vụ tự thành nút `FAQPage`; mục FAQ đã tắt không có trong dữ liệu. Schema tùy chỉnh trong CMS (`seo.structuredData`) vẫn thay thế toàn bộ phần tự động như trước. Trang Phần mềm dùng `SoftwareApplication` chỉ khi bảng giá có ít nhất một gói ghi số rõ ràng (`lowestPlanPriceVnd`, ví dụ "199.000đ"; "Liên hệ" không tính) để có `offers`; chưa có thì giữ `Service`, vì Google đòi giá hoặc đánh giá thật cho `SoftwareApplication`, thiếu thì Search Console báo "không hợp lệ". Cố ý không bao giờ tự thêm `aggregateRating` (cần đánh giá thật của khách). CMS có mục "Hướng dẫn SEO cho loại trang này" trong trợ lý SEO (`ui/seo-page-guides.ts`): đổi hành vi JSON-LD/metadata thì cập nhật bản hướng dẫn đó.
- **Tình trạng hàng và tác giả bài viết** (migration `0023_equipment_availability_post_author`, chỉ thêm cột): thiết bị có `availability` (Còn hàng/Sắp hết hàng/Đặt trước/Hết hàng/Ngừng kinh doanh; `equipment/equipment-availability.ts` chứa nhãn và ánh xạ schema.org, không phụ thuộc zod nên cả thành phần chạy ở trình duyệt dùng được). Trang chi tiết luôn hiện nhãn (`AvailabilityBadge always`), danh sách chỉ hiện khi khác Còn hàng; `Product.offers.availability` lấy từ đây; cột "Tình trạng hàng" trong xuất/nhập Excel nhận nhãn tiếng Việt hoặc mã. Bài viết có `authorName`/`authorTitle`/`authorUrl` (mục "Tác giả" trong màn soạn): website ghi dòng "Tác giả: tên, chức danh" (`AuthorByline`, tên là liên kết `rel="author"` khi có trang cá nhân), thẻ `meta author` và `Article.author` là `Person`; không điền thì tác giả là tổ chức như cũ. Gửi bài mà không có các trường này (API/nhập khẩu cũ) thì giữ giá trị đã lưu, gửi `null` là xóa.
- **Trang tác giả** (migration `0024_post_authors`, chỉ thêm; mô-đun `packages/shared/src/server/authors/`): hồ sơ tác giả dùng lại cho nhiều bài (`post_authors`, không cần tài khoản CMS), quản lý ở CMS "Tác giả" (`/admin/authors`) bằng quyền `posts.*` (bật trang công khai, sửa hoặc xóa tác giả đang bật cần thêm `posts.publish`). Bài chọn tác giả bằng `authorProfileId`; hồ sơ thắng ba ô "tác giả khách" nhập tay. Website: `/tac-gia/<slug>` (`app/(web)/author`, ánh xạ trong `legacy-paths.ts`) hiện hồ sơ, danh sách bài (không gồm bài noindex), `ProfilePage` + `Person`, có trong sitemap; **chỉ có khi tác giả đã bật trang và có ít nhất một bài đang hiển thị, không thì 404**. Dòng "Tác giả" trên bài liên kết tới trang này (`lib/author.ts` chọn tác giả hiển thị, `AuthorByline`), `Article.author` là `Person` có `@id` khớp với trang tác giả, hồ sơ ngoài là `sameAs`. Tài nguyên công khai `author` và `author-summaries` ở `/api/v1/public/content`. Không xóa được tác giả khi còn bài dùng.
- **Kiểm tra SEO ở CMS** (`packages/shared/src/server/seo-audit/`): ngoài trùng/thiếu/độ dài, nay báo **noindex** (nội dung đang hiện nhưng không bao giờ lên Google; trang noindex không tính vào so sánh trùng lặp), **canonical trỏ sang tên miền khác hoặc trang khác** (so với `siteUrl`, bỏ qua dấu `/` cuối; chưa cấu hình `siteUrl` thì không đoán) **ảnh bìa thiếu alt** và **tranh từ khóa** (hai nội dung đang hiện cùng từ khóa chính; nội dung noindex không tính).
- **Trợ lý SEO từng nội dung** (`SeoAssistant`, `shared/seo.ts`): ô **Từ khóa chính** (`seo.focusKeyword`, tối đa 80 ký tự; chỉ CMS dùng để chấm điểm, website không in ra vì Google không dùng thẻ meta keywords). Có từ khóa thì kiểm tra thêm từ khóa ở tiêu đề, mô tả, đường dẫn (so không dấu), đoạn mở đầu, đề mục H2/H3 và mật độ 0,5–2,5% (chỉ đo khi bài từ 100 từ). Bài soạn thảo còn được báo ảnh thiếu alt và bài từ 300 từ thiếu đề mục. Trang chỉ chấm tiêu đề, mô tả, đường dẫn vì không có nội dung bài.
- **Khớp từ khóa và cụm từ liên quan** (`matchKeyword`, `normalizeRelatedKeywords` trong `shared/seo.ts`; `seo.relatedKeywords`, tối đa 4 cụm mỗi cụm ≤ 80 ký tự): công cụ không thể biết từ khóa nào là đúng (cần dữ liệu truy vấn thật từ Search Console, chưa nối); nó chỉ kiểm cụm người biên tập khai có xuất hiện không. Khớp ba mức: **nguyên cụm** (đạt); **gần khớp** (≥ 60% số từ của cụm, không cần liền nhau hay đúng thứ tự, cụm từ 2 từ trở lên); **không khớp**. Tiêu đề giữ chặt (gần khớp chưa đạt); đường dẫn thiếu cụm chỉ là gợi ý (từ 19/11/2026, vì đổi đường dẫn bài đã đăng làm hỏng liên kết cũ); mô tả, đoạn mở đầu, đề mục, nội dung: gần khớp tính là đạt (`SeoCheck.partial`) và hiện thành "Gợi ý nhỏ" (tối đa 2, `SeoGuide.hints`), không làm mất trạng thái "Sẵn sàng". Cụm liên quan là cách gọi khác của cùng ý: chỉ kiểm có xuất hiện trong bài (mục `kw_related_1..4`) và báo nhồi khi một cụm ≥ 2,5% số từ; chỉ đánh giá khi bài từ 100 từ và có nội dung bài (bài viết, sản phẩm/giải pháp/dịch vụ; Trang và thiết bị không có ô này). Cụm trùng nhau hoặc trùng cụm chính bị bỏ. Ô nhập một dòng ngăn cách bằng dấu phẩy; website không in các cụm này ra.
- **Dành cho người không rành SEO** (`seoGuide`, `suggestFocusKeyword` trong `shared/seo.ts`; giao diện ở `SeoAssistant`): đầu trợ lý là một điểm "Sẵn sàng lên Google x/y" (xanh khi đủ, vàng khi còn việc) kèm tối đa 3 việc nên làm trước theo thứ tự mô tả → tiêu đề → từ khóa → ảnh chia sẻ → cấu trúc bài; danh sách đầy đủ thu gọn ở "Tất cả mục kiểm tra". Việc có nút sửa nhanh chỉ khi máy làm đúng được: rút gọn tiêu đề/mô tả quá dài (`trimToLimit`: không thêm "…", cắt ở dấu ngăn cách hoặc trước từ nối, kết quả luôn nằm trong khoảng đạt 30–60 / 70–160 ký tự; mô tả ưu tiên kết thúc ở câu trọn vẹn); mô tả quá ngắn, thiếu từ khóa trong tiêu đề, thiếu ảnh bìa, thiếu alt… cần người viết nên không có nút (từng thử tự ghép từ khóa vào đầu tiêu đề, ra tiêu đề rác nên bỏ). Gợi ý cụm từ từ tiêu đề tắt ở trang hệ thống ("Trang chủ" không phải cụm khách tìm). Bản xem trước Google dùng chung `withBrand` với website (chỉ thêm " | iOrder" khi tiêu đề chưa có thương hiệu). Ô "Khách hay gõ cụm từ nào…" gợi ý sẵn từ tiêu đề (`suggestFocusKeyword`). Ngôn ngữ đời thường: "địa chỉ chính thức" thay canonical, "ẩn khỏi Google" thay noindex, "mô tả ảnh (alt)". Khối "Nên có trước khi đăng" (`PrepublishHints`) có thêm dòng "SEO trên Google (còn N việc)" (`seoPrepublishIssues`: tiêu đề, mô tả, từ khóa, alt ảnh; ảnh bìa và tóm tắt đã có dòng riêng); bấm vào thì `focusEditorField` mở các panel thu gọn chứa ô đó (ở đây là "Google & chia sẻ mạng xã hội") rồi cuộn tới trợ lý (`id="seo-assistant"`). Tổng quan có thẻ "Việc SEO nên làm": 5 nội dung nặng nhất từ cùng bộ kiểm tra toàn website, ẩn khi không có quyền xem hoặc kiểm tra lỗi. Khung "Xem trước trên Google" luôn nền trắng vì chữ cố định không đọc được trên theme tối.

### Google Search Console (chỉ đọc)

- **Làm gì:** CMS đọc số liệu tìm kiếm của chính website từ Search Analytics API: thẻ "Cơ hội trên Google" ở Tổng quan (cụm đang hạng 8–20, hoặc đã ở trang đầu nhưng ít người bấm) và mục "Khách đang tìm gì để thấy trang này" trong trợ lý SEO của bài đã đăng (chỉ hiện khi đã nối được; bấm một cụm để điền vào ô từ khóa chính). Màn **Cài đặt → Google Search Console** (`/admin/search-console`) cho người vận hành thấy trạng thái nối, email tài khoản dịch vụ (để thêm vào Search Console, có nút sao chép), website tài khoản thấy, thuộc tính đang dùng, lý do chưa nối được và nút "Kiểm tra kết nối". Khóa nhập ở CMS → Hệ thống → Kết nối & khóa API (chỉ Super Admin, mã hóa, nhập lại mật khẩu) hoặc đặt ở máy chủ bằng biến môi trường (biến luôn thắng). Không có thao tác ghi nào lên Google; quyền xem là `settings.view`.
- **Mã nguồn:** `packages/shared/src/server/search-console/` (`google-auth.ts`: JWT RS256 bằng `node:crypto`, địa chỉ Google là hằng số; `search-console.service.ts`: truy vấn, cơ hội, chọn thuộc tính, bộ nhớ đệm; `search-console.ts`: nối với cấu hình thật), endpoint `GET /api/v1/admin/search-console` (`?path=/tin-tuc/ten-bai` cho một trang, `?diagnose=1` cho "Kiểm tra kết nối"), thẻ `components/admin/search-console-card.tsx` (tải sau khi trang mở), màn cài đặt `components/admin/search-console-settings.tsx`, lệnh `pnpm gsc:check`. Không thêm thư viện.
- **Số liệu:** 28 ngày kết thúc cách hôm nay 3 ngày (Google trả trễ); nhớ trong bộ nhớ 6 giờ, lỗi nhớ 1 phút; Google lỗi khi làm mới thì dùng số liệu cũ đã có. Ngưỡng "cơ hội" (≥ 10 lượt hiện ở hạng 8–20; ≥ 50 lượt hiện, hạng < 8, dưới 2% bấm) là mặc định theo kinh nghiệm chung, không phải quy tắc của Google.
- **Các bước ở phía Google (một lần):**
  1. Search Console → thêm website, chọn thuộc tính "Tên miền" (nên) và xác minh bằng bản ghi TXT trong DNS (đừng xóa bản ghi sau đó). Gửi sơ đồ `sitemap.xml`.
  2. Google Cloud Console → tạo project → bật "Google Search Console API" → tạo Service Account → tạo khóa JSON và tải về.
  3. Search Console → Cài đặt → Người dùng và quyền → Thêm người dùng: dán email của tài khoản dịch vụ (dạng `…@….iam.gserviceaccount.com`), quyền **Hạn chế** (chỉ đọc); API báo 403 mới nâng lên Đầy đủ. Không cấp Chủ sở hữu.
  4. Cách dễ nhất: Super Admin tải tệp JSON lên ở CMS → Kết nối & khóa API (cần `SECRETS_MASTER_KEY`). Hoặc đặt tệp JSON **ngoài thư mục dự án**, rồi trong `.env` đặt `GOOGLE_SERVICE_ACCOUNT_FILE=<đường dẫn tới tệp>` (production: `GOOGLE_SERVICE_ACCOUNT_JSON` là nội dung tệp trên một dòng, bọc nháy đơn; `compose.production.yaml` chuyển biến này cho API). Thuộc tính tự chọn theo địa chỉ website trong Cài đặt "Tên miền & SEO" (ưu tiên `sc-domain:`); chỉ đặt `SEARCH_CONSOLE_PROPERTY` khi muốn chọn thuộc tính khác.
  5. Bấm "Kiểm tra kết nối" ở Cài đặt → Google Search Console (hoặc chạy `pnpm gsc:check`): hiện email tài khoản dịch vụ, các website nó thấy, thuộc tính được chọn và kết quả thử; thiếu gì thì nói cách sửa. Dữ liệu mới thường có sau 2–3 ngày.
- **Bảo mật:** khóa chỉ nằm ở tiến trình API (CMS và website không thấy); không ghi khóa hay mã truy cập vào nhật ký, thông báo lỗi hay phản hồi (có test); đường dẫn trang gửi lên API được kiểm chặt (chỉ đường dẫn tương đối an toàn, tối đa 300 ký tự). Tài khoản dịch vụ chỉ thấy đúng website đã chia sẻ; thu hồi bằng cách gỡ email khỏi Search Console hoặc xóa khóa trong Google Cloud. Nên đổi khóa định kỳ.

### Địa chỉ website trong các nút "Xem website" của CMS

Nút "Xem website" (header), "Mở trang đã xuất bản", "Xem trước bản nháp", liên kết trong danh sách và khung xem trước của trình dựng đều lấy địa chỉ gốc từ `resolveWebsiteOrigin` (`apps/admin/src/lib/website-origin.ts`), tính ở máy chủ CMS theo nơi đang mở CMS rồi chuyển xuống client qua `WebsiteOriginProvider`/`useWebsiteUrl()`; Server Component dùng `getWebsiteOrigin()`. Không cần build lại khi đổi môi trường:

| CMS đang mở bằng | Website trỏ tới |
|---|---|
| `localhost`, IP riêng (192.168.x, 10.x, 172.16–31.x), `*.local`, tên máy không có dấu chấm | Cùng máy với CMS, giữ cổng của `NEXT_PUBLIC_PUBLISH_WEB_URL` (mặc định 3000). Bỏ qua "Địa chỉ website" ở Cài đặt vì tên miền đó có thể chưa trỏ về máy này. Nếu biến môi trường là tên miền thật thì giữ nguyên |
| Tên miền thật | "Địa chỉ website" ở CMS → Cài đặt (đổi ngay, không build lại) → `NEXT_PUBLIC_PUBLISH_WEB_URL` nếu không phải localhost → `http://localhost:3000` |

Sau khi publish chỉ cần điền đúng "Địa chỉ website" ở Cài đặt. Điều kiện cho LAN: website phải mở được qua IP đó (cổng 3000 không bị tường lửa chặn, `next dev` cần `-H 0.0.0.0`). Bản xem trước Google trong trợ lý SEO không dùng địa chỉ của các nút mở trang mà dùng `publicOrigin` (`resolvePublicOrigin`, `usePublicSiteUrl()`): ưu tiên "Địa chỉ website" ở Cài đặt kể cả khi đang mở CMS qua LAN, vì đó là địa chỉ khách thấy trên Google; chưa đặt hoặc là localhost thì dùng địa chỉ như các nút.

## 6. Quy chuẩn giao diện CMS

- **Nội dung nhóm A:** dùng `CmsPageBuilder` chung cho Trang chủ, trang tĩnh/tự tạo, Phần mềm/Giải pháp/Dịch vụ và Thiết bị. Bố cục mới theo yêu cầu sau: Section/Item bên phải, form nội dung ở vùng chính rộng bên giữa; preview mở bằng nút Xem trước trang (dialog lớn, giao diện website 1:1, máy tính/điện thoại) hoặc Cửa sổ riêng để vừa sửa vừa xem; chọn một thành phần hoặc mục con để sửa, kéo thả bằng tay nắm (chuột/cảm ứng), bàn phím dùng Alt + phím lên/xuống, nhân bản, ẩn/hiện, thêm/xóa. Cột phải chỉ có cây nội dung và nút Thêm thành phần; thư viện kiểu hiển thị mở khi cần. Không thêm mục lục lặp. Preview bản đang nhập qua `/api/v1/admin/builder-preview` → bảng tạm TTL 15 phút, chủ sở hữu và sequence → token HMAC → `/cms-preview` vẽ bằng chính route/`PageBlockRenderer` public; không tạo revision hay xuất bản. Khung preview chỉ cho origin CMS đã xác thực nhúng, noindex/no-store và chặn gửi form thật; cửa sổ riêng đồng bộ qua opener + postMessage kiểm origin/source. Chỉ tạo phiên preview khi mở xem trước, không chiếm một cột cố định. Tablet/mobile xếp lại các cột; dùng màu hệ thống, không thêm trang trí. Dữ liệu cũ chưa có blocks thiết bị giữ phần thông tin nghiệp vụ; catalog giữ nguồn nội dung cũ và chuyển qua form chung khi lưu. Nhóm B (bài viết/hướng dẫn) chỉ dùng một `RichTextEditor` qua `PostEditor`, không dùng Page Builder. Nhóm C giữ logic danh sách/hệ thống; các phần CMS và SEO có sẵn tiếp tục dùng nguồn hiện tại. Phần đầu trang danh sách có hero CMS được ListingPageHeader vẽ bằng PageBlockRenderer như homepage, giữ đầy đủ layout/panels/ảnh/nút/appearance. listingLayoutFromBlocks tách hero ra một slot riêng để không lặp trong thân trang; PageHero gọn chỉ là dự phòng khi thiếu hero. Breadcrumb nằm ngoài vùng phủ của hero, metadata/search/phân trang vẫn theo module sở hữu. Cây hero: Phần đầu trang → Bố cục chung + Mục trượt 1, Mục trượt 2…; mỗi mục chứa Điểm nổi bật của chính nó. Mục trượt 1 là nội dung hero chính hiện có, không thêm bản ghi DB. Nội dung từng mục gồm chữ/ảnh/CTA/điểm nổi bật; ảnh nằm ngay dưới tiêu đề. Trường panels[].highlights thiếu thì kế thừa điểm chung (tương thích dữ liệu cũ), mảng rỗng là không có điểm riêng. Có lựa chọn dùng điểm chung; nút thêm trong cây Item luôn hiện cả khi thu gọn nhóm, vô hiệu hóa khi đủ số lượng; Kiểu bố cục và giao diện chỉ chỉnh tại một mục Bố cục chung ở component cha; mục con chỉ có Nội dung. Ảnh chính sửa trong Mục trượt 1. Nhãn Thêm mục trượt khác Thêm thành phần cấp trang. Publish-web giữ mẫu component/font/responsive; cấu hình CMS được áp dụng cho các lựa chọn hỗ trợ, nhịp một màn hình (`PageBlockRenderer screens`) chỉ dùng khi spacing Tự động và hero áp dụng mã neo; trang chủ không bật nhịp này mà dùng bố cục chuẩn `[data-page="home"]`. Kiểu trượt nhiều ảnh không cung cấp điều khiển màu nền/độ rộng vì renderer không hỗ trợ. Khối logo đối tác có mô tả tùy chọn trong `data.description`; logo/tên/liên kết lấy từ module Đối tác & Đánh giá.

- **SEO nội dung:** `ContentSeoEditor` dùng chung và độc lập với builder/Rich Text. Giữ `seoTitle`, `seoDescription`, `canonicalUrl`, slug và redirect 301 hiện có; JSONB `seo` thêm index/follow/sitemap/breadcrumbs, Open Graph, Twitter/X và schema có form theo loại (không nhập JSON). API cũ bỏ `seo` vẫn giữ giá trị đã lưu. Website dùng `contentMetadata`/`ContentJsonLd`, không thêm meta thủ công; sitemap loại noindex và tôn trọng cấu hình indexing toàn website. Lịch sử chứa SEO, tham chiếu ảnh SEO được bảo vệ trong Media Library. Migration 0017/0018 chỉ thêm dữ liệu cấu trúc, không reset DB.

- **Biểu mẫu CMS:** dùng `AdminFormField` cho nhãn tách khỏi lỗi (hướng dẫn nằm ở ⓘ cạnh nhãn, xem hàng Chú thích phụ); `useAdminFormValidation` lấy lỗi từ contract Zod, hiện lỗi cạnh trường và tóm tắt được focus khi submit. Form có kiểm tra Zod dùng `noValidate` để tránh popup lỗi mặc định chặn luồng tiếng Việt. Lỗi API giữ trên form, không chỉ nằm trong toast; giữ bản nhập khi lỗi/409. Cài đặt chỉ nhận trạng thái đã lưu sau khi phản hồi dữ liệu và `version` hợp lệ; `markSaved(savedValue)` ghi baseline đã chuẩn hóa. Tài khoản chỉ xem thấy lời giải thích và trường bị khóa.

Màu đặt bằng token `--cms-*` trong `apps/admin/src/styles/tokens.css` (có bản tối); không viết mã màu trực tiếp trong component.

| Trạng thái | 5 tông `neutral`, `info`, `success`, `warning`, `error` (`--cms-status-*`) qua `AdminStatusBadge`/`AdminNotice` | Theo `content-status-choice.tsx`: nháp và lưu trữ = neutral, chờ duyệt = warning, hẹn giờ = info, đang hiển thị = success; lỗi = error |
| Nhận diện theme | Mỗi bảng màu ngoài màu nhấn còn ghi đè bộ token nhận diện ở `tokens.css`: thanh bên (`--cms-nav-*`, có thể nền tối hoặc chuyển sắc), đường nhấn dưới thanh trên (`--cms-topbar-accent`), nút chính (`--cms-primary-fill`), nền trang (`--cms-background-image`), đổ bóng thẻ (`--cms-shadow-card`), font tiêu đề (`--cms-heading-font`), độ bo góc và độ cao điều khiển. Thanh bên (nav) luôn đậm hơn thanh trên (header): nav đậm với chữ sáng và logo chữ sáng, header tông sáng cùng hệ màu với chữ theo `--cms-text`; cả hai khác vùng nội dung, `--cms-topbar-bg` phải là màu đặc. Chữ sáng trên nav phải đạt tương phản: chữ ≥ 10:1, chữ phụ ≥ 7:1, chữ/icon mục đang chọn ≥ 7:1 / 4.5:1 (test `cms-theme` kiểm). Giá trị mặc định ở `:root` là iOrder Blue. Thanh bên nền tối phải thêm id theme vào danh sách chọn logo chữ sáng trong `shell.css`; màu thanh bên cũng khai báo ở `admin-theme-settings.tsx` (`nav`) cho ô xem trước. Component chỉ dùng token, không kiểm tra id theme | Thanh bên, thanh trên, `.admin-card`, `.admin-button--primary`, h1–h3 |
| Loại tệp | Mỗi loại một màu cố định qua mọi theme sáng (`--cms-file-*`): Excel xanh lá, CSV xanh ngọc, Word xanh dương, PDF đỏ, ZIP vàng nâu, ảnh tím, khác xám. Hiển thị bằng `AdminFileIcon` + `fileKindOf(mime hoặc tên tệp)` trong `ui/admin-file-icon.tsx` | Menu Nhập / Xuất, khung nhập, Thư viện hình ảnh & tệp, ô chọn tệp, Hỗ trợ cài đặt |
| Xuất / nhập | Xuất (tải về) = mũi tên xuống, nhập (tải lên) = mũi tên lên ở góc ô biểu tượng (`action="export"`/`"import"`). Nút tải một định dạng: `admin-button--export admin-file-tone--<loại>` (nền nhạt màu loại tệp); nút phụ cùng định dạng: `admin-button--ghost admin-file-tone--<loại>` (chỉ tô biểu tượng) | Nút "Nhập / Xuất", "Xuất Excel" ở Khách hàng tiềm năng, link "Tải bản Word" |
| Thao tác hàng loạt | Chọn nhiều dòng (cột checkbox của `AdminDataTable`) thì thêm "Đã chọn n" và "Bỏ chọn" cạnh nút "Thao tác ▾" (`AdminBulkBar` + `AdminBulkMenu`); nút này luôn hiện cùng dòng ô tìm kiếm của `AdminFilterBar`, cao bằng các nút lọc. Màn không có thanh lọc thì thanh riêng hiện trên bảng khi đang chọn. Mục menu chỉ một dòng chữ; mục không áp dụng được thì mờ, lý do hiện khi rê chuột. Nội dung có vòng đời dùng `ContentBulkBar`: xuất bản, chuyển về nháp, lưu trữ, khôi phục, xuất Excel các mục đã chọn (`?ids=`), xóa mục đã lưu trữ | Mọi màn danh sách: bài viết, sản phẩm, thiết bị, trang, hỗ trợ cài đặt, đối tác/đánh giá, chuyển hướng, chuyên mục/thẻ, khách hàng, media |
| Chân trang danh sách | `AdminPagination` (`ui/admin-pagination.tsx`): `Tổng N <unit>` (truyền `unit`: "bài viết", "tệp"…) · `Hiển thị [select] dòng/trang` · `‹ 1 2 3 … 12 ›` (đúng 7 ô khi từ 8 trang, `pagination-model.ts`) · `Đến trang [ ] Đi` (Enter cũng nhảy; số quá lớn về trang cuối). Dính đáy vùng cuộn (`position: sticky`; thẻ danh sách dùng `overflow: clip` thay `hidden` để sticky hoạt động; trang có chân trang bỏ đệm đáy 56px của `.admin-shell__scroll` và lề đáy của `.admin-page` (khi phần có chân trang là phần cuối) để lúc cuộn hết chân trang vẫn sát đáy thay vì dừng cách đáy), tắt dính ở ≤700px vì chân trang cao ~117px. Mọi danh sách dùng chung, truyền `onPageSizeChange` để có ô chọn số dòng; màn dùng URL lấy `pagination` từ `useListNavigation()`. `?pageSize=` chỉ nhận 5–100 (`validPageSize`) | Mọi bảng danh sách (kể cả Nhật ký, Media) |
| Thao tác trên dòng | `admin-content-actions__*`: sửa = màu chính, lưu trữ = cảnh báo, khôi phục = thành công, xóa = lỗi; xem/tải giữ trung tính | Cột "Thao tác" của mọi bảng |
| Nút chính | Mỗi màn một nút `primary` (tạo mới/lưu); còn lại `secondary`/`ghost`; thao tác phá hủy dùng `danger` kèm hộp xác nhận | Thanh tiêu đề, thanh lưu |
| Chú thích phụ | `AdminHelpTip` (`ui/admin-help-tip.tsx`): biểu tượng ⓘ cạnh nhãn/tiêu đề, nội dung mở khi rê chuột, focus hoặc chạm (Esc để đóng), vẽ qua portal nên không bị `overflow`/`transform` cắt. Lời giải thích cố định không chiếm dòng riêng: `AdminFormField hint`, `AdminEditorSection description`, `MediaPicker hint`, `LayoutPicker` (`hint`, `note`), `AdminPageBarHelp` (mô tả màn trên thanh vị trí), `AdminDetailPanel help`, `AdminHintedField` (bao ô `<label className="admin-field">` lồng, nút nằm ngoài label); mục menu và thẻ lựa chọn dùng `title`. Trạng thái, cảnh báo, lỗi, thông báo thiếu quyền, trạng thái rỗng và dữ liệu thật (địa chỉ, số liệu, bản xem trước) vẫn hiện sẵn | Mọi form, trình soạn thảo, trình dựng trang, màn cài đặt |
